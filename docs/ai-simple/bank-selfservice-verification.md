# 合并银行流水自助旅程验证

状态：2026-09-12 总控完成统一测试、正式构建及本机浏览器原文件验收，结果见末尾。实施任务仅编写虚构测试源码，没有读取用户原文件或自行执行验证。

范围：普通用户在空工作台上传一份包含三个本方银行账户的合并 Excel，程序识别日期、时间、账户和金额，提供全量核对；用户只确认业务账户与导入事项，随后真实保存并可重载。测试不提供列号或手动 mapping，不扩展跨工作表合并。

## 虚构数据与独立断言

- 使用常见的 13 个中文字段名；账户、银行、交易对手、金额与原始行全部虚构，仅在测试内生成 Excel Blob，不保存测试文件或外部凭证。
- 小表交错排列三账户，共 15 行。每账户三笔同日同额同名同摘要收款，其中两笔同秒但余额不同；另有一笔支出与一条完全相同重复。应保留 12 笔合法交易、识别 3 条真正重复，禁止按旧的日期/金额/对手/摘要键误删。
- 大表生成 432 笔合法交易，每账户 144 笔，用不同交易时间及余额区分。核对摘要须覆盖全部 432 行，不能把预览或模型上下文的有限样例当成全量。
- 本方账号分组；对方账号故意相同，防止把三家银行错误合并。逐组确认只能保存该组原始行及原件关系，重传和重复确认不能增倍。确切同一原件的全部分组已导入后，再次读取返回 `already_imported` 与各组零新增结果，不新增待确认事项或再要求确认。
- 失败后保留原件和可继续的未完成组；权限、归档和目标变化仍阻止财务写入，准备建议不能代替用户确认或凭证入账。

| 432 行与模型协议 | 真正送入受控模型的工具消息仍有全部三个账户和每组 144 行、收入 2448；确认后重载仍保存 432 行，紧凑交易时间有值 |
| 新状态有限存储 | 保留默认演示账本，固定 5 MiB 容量，412/12/8 分组及 13 列中等长中文，全部正常确认并重载，原始字段、原件和其他工作台不删减 |
| 旧状态有限存储继续 | 独立初始化完整 applied.result 冗余 424 笔的旧主快照及较早有效备份，两份逐项通过相同 5 MiB 限制的 setItem；重新打开后最后 8 笔仍可一次确认，原始字段、原件与幂等断言保持 |
| 原子保存与恢复 | 在 `repository.save` 抛出虚构失败，账户/流水/确认状态都不落库；恢复后只保存一次，再次确认不写入，另两组保持待确认 |
| 错误组与补充原件 | 不存在的日期返回源文件行号；该组不可确认，好组可独立完成；补充正确原件后只新增尚未保存的四行，两份原件均保留 |
| 错账户选择 | 与本方账号冲突的业务选择返回错误预览，不替换原有效待确认项；原组仍可确认且不向错误账户写入 |
| 缺本方账号 | 保留分组并要求业务账户选择，选择后重新预览，旧建议失效；确认前不创建账户 |
| 模型失败后继续 | 受控上游 503 不执行工具/导入；已保存三组待确认项可重载，用户仍可本地确认一组 |
| 权限与归档 | 两个独立子用例验证失去写权限、账期已归档时不改存储，原件与三组待确认项保留 |
| 确认期间切期 | 原件校验期间切到下一期，阻止新账户和该组流水写入 |

共十一个顶层旅程，权限/归档另含两个子用例。这是源码覆盖清单，不是通过数量。另经总控授权，`tests/ai-finance-service.test.mjs` 仅适配本轮公开返回协议变化，保持原件、取消、幂等和旧确认失效的行为保护。

容量用例的补充原因：原 432 行夹具已经保留默认演示账本，但三账户均分 144/144/144、中文字段很短，且内存存储没有上限。新用例按全部键名和键值的 UTF-16 字节数计费，每次 `setItem` 在覆盖前计算总占用，超过固定 5 MiB 抛出 `QuotaExceededError` 且不改原值。预算不会随数据增长，也不通过清除备份或演示账本让测试通过。用例首先证明确实会拒绝超限写入。新状态正常保存与旧状态恢复分为两个独立用例；后者通过有限仓库序列化旧主快照，再用同一有限 setItem 初始化较早有效备份，避免在接近满额的现有新主副本之上人为叠加一代更大的旧主快照。初始化失败时诊断输出实际拒写字节数，不能静默提高预算或跳过配额。

各阶段诊断只输出虚构文件的压缩 XLSX 字节数、原始表 JSON 的 UTF-16 字节数、全部键值的 UTF-16/UTF-8 大小、已接受写入峰值与超限次数。压缩文件大小不能代表仓库里的 JSON 主副本总量。此有限模型用于重现容量约束，不能替代真实浏览器配额与用户现场继续操作的验收；备份写入允许沿既有规则在主保存成功后尽力轮换，不能把可恢复的备份拒写等同于主保存失败。

全量运行另发现两处旧协议预期，经总控补充授权适配：`tests/ai-simple-journey.test.mjs` 将缺业务账户从通用 `needs_input/error` 改为 `needs_correction` 和保留的不可确认事项，继续验证失败后的原件、待确认项及重载；`tests/deepseek-assistant.test.mjs` 将固定工具数量从五个改为六个，并断言包含 `read_bank_statement`，保留原客户端/代理三轮完整工具调用循环。

## 证据边界

`tests/bank-selfservice-journey.test.mjs` 通过实际 AI 财务服务、共享财务核心、内存文件库和本地仓库序列化进行验证。模型响应若使用既有脚本适配器，仅代表受控协议证据，不代表 DeepSeek 自主理解或真实服务连接；浏览器中的账户确认界面、超时继续出口及真实 API 由总控另行验收。

静态阅读发现旧链路强制预建账户、由模型/调用方补零基列映射，旧集成测试也显式传 mapping。新增自助旅程覆盖消除这些依赖后的产品行为，不能沿用人工补参来宣称可用。另已向相邻任务指出紧凑时间在 Excel 数值中丢失前导零、模型工具结果体积裁剪可能遗漏完整分组摘要；相关断言保留，实际是否修复须由总控执行结果证明。

本轮遵循现有账户记录只保存后四位的规则；完整虚构账号保留在原件及来源分组。不同真实账户恰好同尾号时维持明确阻断、不得混组，作为剩余项，不扩展基础账户结构。同一工作簿跨工作表合并不在本轮范围。
